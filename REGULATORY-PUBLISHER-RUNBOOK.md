# Regulatory publisher operations (preview only)

The monitoring Worker discovers candidate changes. The separate publisher validates signed packages and advances the D1 head using a compare-and-swap. No production rule or website release permission is granted.

## Enrollment prerequisites
- Confirm the exact deployed calculator engine fingerprint and matching publisher revision.
- Appoint an independent statutory reviewer and a trusted rule publisher. The reviewer must inspect original legal sources, effective periods, jurisdiction, eligibility, dependent calculations and independently derived expected fixtures. Synthetic CI evidence is never a statutory approval.
- On the trusted publisher's controlled offline system, run `node scripts/generate-rule-signing-key.mjs /absolute/path/to/new-private-directory`. Keep private.pem offline with restricted permissions and backups; never commit, upload to the monitor, or paste into chat. Share only public.json.
- Use the reviewed schema-v2 payload (regional, India salary, payroll and national/investment registries), per-component evidence and fixtures. Sign with scripts/sign-preview-rules.mjs. The signature proves publisher identity and integrity, not legality.
- The independent reviewer generates a separate offline Ed25519 key, checks the actual legal evidence and independent fixtures, and runs `node scripts/approve-preview-rules.mjs PACKAGE.json PUBLISHER_PUBLIC.json REVIEWER_PRIVATE.pem REVIEWER_ID OUTPUT.json I_HAVE_INDEPENDENTLY_REVIEWED_THE_STATUTORY_EVIDENCE`. This binds the reviewer identity, exact snapshot digest, engine fingerprint and sequence. Never use CI keys as statutory approval.
- Configure a SQLite-backed Cloudflare Durable Object namespace for the exported class `RegulatorySequenceAnchor` from `staging/publisher-worker.mjs`, and bind it to the publisher as `REGULATORY_SEQUENCE_ANCHOR`. Apply the Worker migration that creates the SQLite-backed class before enabling any schedule. This Durable Object is the authoritative, strongly consistent monotonic sequence anchor and is independent of D1. Its initial row is created at sequence 0/state empty. The separate KV binding `RULE_SEQUENCE_FLOOR` is only a non-authoritative diagnostic mirror; it must never be used as a substitute for the Durable Object because KV is eventually consistent. Keep key `taxpulse:regulatory-sequence-floor` aligned for observability, but publication and rollback decisions must use the Durable Object RPC methods.
- Configure the publisher with RULE_REVIEW_PUBLIC_KEY and RULE_REVIEWER_ID as well as RULE_PUBLIC_KEY. The scheduled publisher rejects missing, reused, invalid or mismatched approvals. The publisher and reviewer keys must differ. Preserve the original reviewed package in the reviewer's controlled archive. After migration 004, each newly published D1 snapshot atomically stores the signed reviewer attestation and both public keys alongside the publisher envelope. Archived keys enable later cryptographic inspection but do not independently establish trust or revocation status. Earlier snapshots, if present, are not retroactively approved. Apply migration 004 once before deploying the updated publisher; keep the schedule disabled during the cutover.
- Enroll the same publisher and independent reviewer public keys and reviewer identity on both the preview publisher and runtime; enable the publisher schedule only after enrollment. The publisher reads RULE_INBOX and writes RULE_DB; preview reads RULE_DB, RULE_PUBLIC_KEY, RULE_REVIEW_PUBLIC_KEY, RULE_REVIEWER_ID and RULE_MIN_SEQUENCE. It verifies the independent approval again on each signed load; legacy KV-only signed mode is rejected. Do not bind the preview runtime to an empty head: this intentionally blocks statutory calculation.
- Verify the first approved package in the private publisher, confirm D1 head, exact engine fingerprint and hosted smoke results, then bind the reader. Reissue signed snapshots before their expiry; otherwise the runtime fails closed.
- Emergency restriction advances the Durable Object sequence anchor before the D1 head. The publisher compares D1 against the anchor on every run. If a D1 restore rolls the head behind the anchor, the first publisher run blocks the restored head; recovery then requires a newly signed snapshot whose sequence is greater than the durable anchor. It never lowers the anchor or replays an old envelope. KV may mirror the new sequence for diagnostics but is not authoritative. Keep previous Worker versions and D1 history. Key rotation requires coordinated public key and publisher enrollment. Disable publication, block the current head, advance the Durable Object anchor above the old sequence, replace the affected trusted key on both publisher and runtime, and publish a newly reviewed higher-sequence snapshot. An old archived key is evidence, not current authority. If any step fails, retain the blocked state; never fall back to KV or lower the anchor.
- Schema v1 snapshots cannot activate with v2. Historical catalog is independently bundled; the 2026 national registry supports only the currently modeled period and shape. Unmigrated legacy country calculations are blocked in signed mode.

## Staging verification
The hosted preview check is a separate read-only GitHub Actions workflow triggered by data/hosted-preview-check.json changes; pin the expected deployment revision, monitoring source count and runtime state. A CI test of the local bundle does not by itself establish that the hosted revision works. Never label a failed or unexecuted hosted check as passed.
